CSV import errors explained: the exact messages and what causes them

Every importer fails in a small number of ways, and it usually tells you which one in a sentence nobody explains. These are the ten failures that account for almost all of it: the literal message or symptom, what is really in the file, a thirty-second way to prove it, and what fixes it.

One thing worth saying before the list: a CSV has no types, no schema and no escaping rules beyond "wrap it in double quotes". Everything below is a consequence of that. The file is almost never corrupt — it is doing exactly what the text says, and the importer is reading it the way the specification says to.

1. "Row 43 has 12 fields but the header has 9"

What you see: the importer refuses the whole file, naming one row number, or it imports and every column after a certain point is shifted by one to the right.

What is actually wrong: the row contains a comma that the importer counted as a separator. Three things cause it:

  • a value like Smith, John or Blue, large that was never wrapped in double quotes;
  • a quote that opened and never closed, which makes every comma after it part of the text — and usually eats the row break too;
  • a trailing comma at the end of the line, which adds one empty field to that row only.

Prove it in 30 seconds: open the file in a plain text editor (Notepad, TextEdit, VS Code — not Excel, which hides this), go to the row number the importer named, and count the commas outside quotes. If the count differs from the header line, you have found it.

Fix: wrap the offending value in double quotes, and double any quote that appears inside it: "Smith, John" and "12"" screen". Never "fix" it by deleting the comma — that changes the data. If it is one row out of thousands, the cleaning tool can find and quote it for you: clean the CSV in the browser first and re-upload the downloaded copy.

2. Everything lands in one column, commas and all

What you see: the import succeeds, but each row has a single cell containing the entire line.

What is actually wrong: the file is not comma-separated. Either it uses semicolons (normal in countries where the decimal separator is a comma, because otherwise 1,50 would break the row), or it uses tabs and was saved with a .csv extension.

Prove it: look at the first line in a text editor. No commas in it means the importer is right and the file is the problem.

Do the separator conversion before the decimal conversion, and do not do them in the same pass: converting semicolons first turns 1,50 into two fields, which is exactly failure number 1.

3. An invisible character sits before the first header name

What you see: the header cell reads fine, but the importer says the column sku does not exist. Sometimes the first header shows as ï»¿sku, ﻿sku or an empty box.

What is actually wrong: a UTF-8 byte-order mark. Three bytes, EF BB BF, at the very start of the file. Spreadsheets hide it; string comparison does not. Excel writes it by default when you save as "CSV UTF-8", and many libraries read it as part of the first field.

Prove it: in a text editor, put the cursor before the first letter of the first header and press Backspace once. If the header still looks identical but the import now works, that was it.

python3 -c "print(open('file.csv','rb').read(3))"   # b'\xef\xbb\xbf' means BOM

Fix: save as "CSV (comma delimited)", not "CSV UTF-8", or have the importer strip it. Stripping is safer — the BOM is the only thing that makes accented names survive Excel on Windows, so removing it at the front of the pipeline rather than at the source avoids a different bug later.

4. Amounts arrive as text, and totals refuse to add up

What you see: a column of numbers left-aligned in the sheet, a green warning triangle, and SUM returning zero.

What is actually wrong: the cell is text that looks like a number. The usual culprits, in order of how often they occur:

  • a currency symbol or code in the same cell: $12.00, 12.00 USD;
  • a thousands separator: 1,234.56 — and in European files 1.234,56, where both the roles are reversed;
  • a non-breaking space, which looks exactly like a normal space and is not;
  • a trailing minus sign, as in 123.45-, which some accounting systems export;
  • a leading apostrophe, which forces text in Excel and is invisible in the cell.

Prove it: select the column and look at the status bar. If it shows Count but not Sum, the values are text.

Fix: reduce every amount to digits, one decimal point and an optional leading minus, then convert. The order matters: 1,234.56 and 1.234,56 must be told apart by looking at the last separator in the string, not by assuming.

5. Dates swap day and month, or are rejected with "invalid date"

What you see: an order from 3 April becomes 4 March, or the importer rejects the column entirely.

What is actually wrong: 04/03/2026 is two different dates depending on who wrote the file, and the file does not say which. Related failures: Excel serial numbers (45291), timestamps with a timezone offset, and month names in a non-English locale.

The uncomfortable part: any tool that "just fixes" an ambiguous date is guessing. If 30% of your rows have a day above 12, you can infer the convention from those rows — but if all of them are below 13, there is no evidence in the file at all, and the only correct output is a flag, not a value.

Fix: export dates as ISO 8601 — 2026-03-04 — end of debate. If you cannot change the export, sort the file and check whether any day exceeds 12; that single fact decides the convention for the whole column.

6. The row count doubles, or duplicates appear out of nowhere

What you see: 1,000 rows in the file, 1,000 rows in the table before, 2,000 after.

What is actually wrong: one of three things:

  • the import appends instead of replacing, and the file contained the rows that were already there — the most common cause by far;
  • a line break inside a quoted value (a multi-line address, for example) is being treated as a row break by a reader that does not handle quoted newlines;
  • a trailing empty line at the end of the file is imported as a blank record, which then looks like a duplicate of "nothing".

Prove it: if the duplicates are every row, it is the append/replace setting. If only some rows appear twice, sort by a column and look at the neighbours of the doubled rows — a wrapped address will be there.

Fix: delete the destination rows before importing, and de-duplicate on a real key (order id, SKU) rather than on the whole row: two orders can legitimately be identical in every column except the id.

7. "Column sku not found" — but the column is right there

What you see: the mapping screen cannot match a header you can plainly see in the file.

What is actually wrong: the header string is not the string you think it is. In practice: a trailing space after the last header, a non-breaking space inside it, a BOM (number 3), different capitalisation, or a smart quote pasted from a document. Headers copied out of a PDF are the worst offenders.

Prove it: in a text editor, move to the end of the header line and press End. If the cursor stops one character short of the line break, there is a space there.

Fix: trim the header line, and keep a copy of the trimmed headers next to the file so the next import is not a new investigation.

8. "Codec can't decode byte 0x92" (or any other 0x8x / 0x9x byte)

What you see: a Python, Ruby or Node script dies on the first line, naming a byte position.

What is actually wrong: the file is Windows-1252, not UTF-8. Byte 0x92 is the curly apostrophe in Smith’s; in UTF-8 that character is three bytes. Excel on Windows writes this encoding by default when you choose plain "CSV".

Fix: read with encoding="cp1252" and write back as UTF-8 — but check first that the file really is cp1252 everywhere and not a mixture, which happens when two people export into the same file.

python3 -c "d=open('file.csv','rb').read(); d.decode('utf-8'); print('utf-8 ok')"

9. Blank rows at the end, or in the middle

What you see: an extra empty record, a count that is one higher than expected, or an error about a row that looks empty in the spreadsheet.

What is actually wrong: every CSV file ends with a line break, and a reader that splits on line breaks produces an empty final element. If the file was edited by a spreadsheet after export, deleted rows also leave lines containing only separators — ,,, — which are not empty strings and pass a naive "is it blank" test.

Fix: drop rows where every field is empty after trimming. That handles both shapes, and it is the one cleanup that is always safe.

10. The import times out, or stops at exactly 1,000 / 10,000 rows

What you see: a generic error, or a successful import with fewer rows than the file contains.

What is actually wrong: a request size or time limit, not a data problem. The "exactly 1,000" pattern means a default page or batch size is being applied somewhere between the file and the table.

Fix: split the file into batches on a column you can sort by, import in order, and count the rows after each batch. If the count matches the file, the importer is fine and the failure was size. Do this before spending an hour hunting for a corrupt row that does not exist.

How to tell which one you have, in one pass

  1. Open the file in a text editor, not a spreadsheet. Look at the first line: does it contain commas?
  2. Count the commas on the header line, then on the row the importer complained about.
  3. Put the cursor before the first character of the header and press Backspace once.
  4. Move to the end of the header line: does End stop short of the line break?
  5. If the errors concern dates or amounts, look for the ambiguous shapes above rather than for corruption.

That is five minutes, and it identifies the cause in nearly every case. The remaining ones are usually a value that looks right in the sheet and is not right in the file — which is exactly what a browser-side cleaner with a flag list is for.
